The Firebolt Operator manages five custom resources:

- **FireboltInstance** provisions shared PostgreSQL, Metadata Service, and Gateway infrastructure in a namespace.
- **FireboltEngine** runs the compute nodes that serve queries.
- **FireboltEngineClass** provides optional shared defaults for Engines in the same namespace.
- **ClusterFireboltEngineClass** is an optional cluster-scoped SKU catalog (instance type, resources, node setup). See [ClusterFireboltEngineClass CRD reference](./crd-reference/clusterfireboltengineclass-crd-reference).
- **FireboltEnginePreset** is an optional ambient overlay merged under every Engine in the namespace (service account, storage, credential env, `customEngineConfig`). See [FireboltEnginePreset overview](./enginepreset/overview).

## Resource relationships

```text
                         optional shared defaults
                  ┌──────────────────────────────┐
                  │ FireboltEngineClass          │
                  │ (namespaced, wins same name) │
                  └──────────────┬───────────────┘
                                 │
                  ┌──────────────┴───────────────┐
                  │ ClusterFireboltEngineClass   │
                  │ (cluster SKU catalog)        │
                  └──────────────┬───────────────┘
                                 │
                                 ▼
┌──────────────────────┐   1:N   ┌──────────────────────┐
│ FireboltInstance     │◄────────│ FireboltEngine       │
│                      │         │                      │
│ PostgreSQL           │         │ Stateful compute     │
│ Metadata Service     │         │ Query processing     │
│ Gateway              │         │ Per-Engine Service   │
└──────────────────────┘         └──────────────────────┘
```

Every Engine references one Instance in the same namespace through `spec.instanceRef`. The Instance must publish a ready Metadata Service before the Engine can start or materialize configuration in the `stable`, `stopped`, or `creating` phases. The Engine reports `InstanceReady=False` and waits when that gate fails. The `switching`, `draining`, and `cleaning` phases operate on already-rendered resources. Routing publication and retirement still read the Instance and its coordination state.

The same scheduling window applies to the fail-closed EngineClass and FireboltEnginePreset gates. When a namespaced class is not Ready for an operator-owned template path, a `ClusterFireboltEngineClass` live spec fails the SKU-only or operator-owned check, or Preset is required and missing, or not Ready for an operator-owned path, the Engine stays not Ready and does not render a StatefulSet. The `switching`, `draining`, and `cleaning` phases finish that rollout anyway. The Firebolt Operator may still read the EngineClass while draining, for inherited drain settings (`rollout`, `drainCheckEnabled`, drain interval). It does not fail closed on those reads.

An Engine may also set `spec.engineClassRef` to a class name. The Firebolt Operator resolves that name namespaced-first: a `FireboltEngineClass` in the Engine's namespace if present, otherwise a `ClusterFireboltEngineClass` of the same name. Settings resolve Engine, then FireboltEnginePreset, then the resolved class, then Firebolt Operator defaults. See [EngineClass configuration inheritance](./engineclass/configuration-inheritance).

### External metadata PostgreSQL

When `FireboltInstance.spec.metadata.postgres` is present, the Firebolt Operator
does not create the internal PostgreSQL StatefulSet. It renders the supplied
host, port, database, and schema into the Metadata Service configuration and
mounts the referenced Secret directly; credential bytes are not copied into the
Instance or ConfigMap.

The optional `spec.metadata.postgres.tls` block requires libpq `verify-full`
certificate and hostname verification. The Firebolt Operator projects only the
selected key from a same-namespace CA Secret into the Metadata container and
sets `PGSSLMODE` and `PGSSLROOTCERT`; sidecars cannot mount the operator-owned CA
volume.

The Instance controller watches referenced credential and CA Secrets. It folds
their `resourceVersion` values into the Metadata Service pod-template hash, so
an in-place credential or CA rotation rolls the single metadata pod even though
the Secret names and rendered configuration remain unchanged. The hash never
contains Secret bytes.

## Query traffic

Clients connect to the Instance Gateway and select an Engine with the `X-Firebolt-Engine` header or `engine` query parameter. Direct Engine Services and Pod IPs are not supported client entry points.

Each Gateway Pod runs Envoy and the mandatory local agent. Envoy validates the Engine selector, then uses `ext_proc` to request admission. The agent records the admission before returning a generation-specific authority. SQL and result bodies remain in Envoy. A request retains its generation across retries, and its local accounting remains outstanding until Envoy signals that no future dispatch is possible. An uncertain processor termination retains liability rather than assuming completion.

The Firebolt Operator owns a routing ConfigMap per Instance, separate from Envoy's static configuration. It contains generation assignments, revisions, registered Pod UID/agent boot sessions, and outstanding retirement records. Agents watch it using read-only Kubernetes credentials and report applied revisions and local counts; there are no per-query Kubernetes writes. A registered agent keeps serving its authorized route during a Firebolt Operator restart.

Generation query Services are headless and ready-only, with immutable selectors and names derived from Engine UID and generation. Peer-discovery Services still publish not-ready addresses for cluster formation. Envoy resolves query Services by exact fully qualified DNS names. DNS refresh and active health checks determine usable hosts inside the assigned generation; neither constitutes permission to retire that generation.

The Gateway retries only failures establishing that the Engine has not processed the request: connection failures, refused streams, resets before request headers are sent, and pre-work shutdown responses marked `X-Firebolt-Drained`. Other resets after request delivery and arbitrary HTTP 5xx responses are returned to the client because replay could duplicate a write.

See [Gateway overview](./instance/gateway/overview) for connection examples and [Gateway query routing](./instance/gateway/gateway-query-routing) for the admission and withdrawal protocol.

### Gateway termination

During planned Gateway pod termination, Envoy's pre-stop hook fails readiness and drains the inbound query listener. It closes that listener to new connections while existing query connections finish, including requests parked for Engine wake-up. The metrics listener and local admin interface remain available. The hook waits for the query listener's downstream connection count to reach zero before returning; Kubernetes then sends SIGTERM to Envoy.

The agent runs as a Kubernetes native sidecar after user-provided init containers. Kubernetes keeps it running until the main containers, including Envoy, have stopped, so routing and wake handling continue during draining. This ordering requires Kubernetes 1.33 or later. The agent checks routing usability before granting a held request; this check is separate from the withdrawal acknowledgment.

The Gateway pod's shutdown budget defaults to 180 seconds and can be set with `spec.gateway.template.spec.terminationGracePeriodSeconds`. The budget covers wake waiting, remaining query execution, and container shutdown. Kubernetes forcibly terminates remaining containers when the budget expires. Gateway listener draining protects accepted requests within that budget; it does not acknowledge propagation through an external load balancer or replace an Engine traffic-withdrawal gate.

## Engine availability

The Firebolt Operator applies Engine changes with blue-green generations:

1. It creates the desired generation and waits for every Pod and readiness-aware sidecar.
2. It publishes the replacement route and closes the old assignment, durably recording its registered Gateway holders.
3. Every holder applies the fence and reports that its old admissions and uncertain requests are zero. A positively observed stop of that Envoy process can also clear its liability.
4. For graceful rollouts, metric drain checks additionally wait for Engine query activity to finish.
5. Only after withdrawal can the Firebolt Operator remove old Engine Pods and Kubernetes send SIGTERM.

The withdrawal gate also covers scale-to-zero, deletion, and cleanup paths; `recreate` and disabling metric checks do not bypass it. Missing reports, stale session identities, or unknown admissions block retirement. A changed agent boot identity in the same Pod cannot erase old accounting. The Firebolt Operator replaces that Gateway Pod; a finalizer retains its terminal status until positive Envoy termination evidence has been recorded. Pod absence, readiness, and timeout are not substitutes for that evidence.

Plan enough cluster capacity for both Engine generations and Gateway replacements. Accepted Engine work must finish within the Pod termination budget, and the Engine's shutdown accounting must include connections queued before query-handler execution. Budget expiry can interrupt unfinished requests. See [Engine rollouts](./engine/engine-rollouts).

## Instance-wide security

Authentication and listener TLS are configured on the Instance and apply consistently to its Engines:

- `spec.auth` configures local authentication and optional OIDC validation.
- `spec.tls.engine` configures TLS between the Gateway and Engines.
- `spec.tls.gateway` configures client-facing Gateway TLS and optional mutual TLS.

The Instance reports authentication and TLS readiness independently through `AuthReady`, `EngineTLSReady`, and `GatewayTLSReady`. See [Security](./security) for configuration, certificate, Secret, and network-policy guidance.

## Storage

Engine pod storage and managed-table object storage are separate settings:

- `spec.storage` selects the pod data volume backend: `emptyDir`, `hostPath`, or a persistent volume claim template.
- `spec.customEngineConfig.storage` configures the object store used for managed table data.

See the [FireboltEngine CRD reference](./crd-reference/engine-crd-reference) and the [object storage guides](./engine/object-storage/amazon-s3).
