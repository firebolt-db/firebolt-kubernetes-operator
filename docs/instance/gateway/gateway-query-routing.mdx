The Instance Gateway is the supported entry point for client queries. Direct Engine Services and Pod IPs are internal destinations.

## Select an Engine

Use either the `X-Firebolt-Engine` header or the `engine` query parameter:

```bash
curl -H 'X-Firebolt-Engine: my-engine' \
  http://<gateway-address>:8080/
```

```bash
curl 'http://<gateway-address>:8080/?engine=my-engine'
```

If both selectors are present, they must name the same Engine. Engine names must be valid lowercase RFC 1123 DNS labels: letters, numbers, and hyphens, with no leading or trailing hyphen.

The Gateway removes the routing-only `engine` query parameter before forwarding the request.

## Traffic path

```text
Client -> Gateway Service -> Envoy -> generation-specific Service -> ready Engine Pod
                              |
                              +-> local agent: request admission and completion
```

Envoy validates the Engine selector, then asks its local agent to admit the request through the `ext_proc` filter. The agent records an outstanding request before returning an immutable generation destination. SQL and result bodies pass through Envoy; they are not sent to the agent. Each admitted request keeps its destination across Envoy retries.

The Firebolt Operator publishes routing assignments and registered Gateway sessions in a separate coordination ConfigMap. A session combines a Gateway Pod UID with the agent's process identity. The agent watches this ConfigMap and reports its applied revision and outstanding requests. Admission and completion update local memory; they do not write Kubernetes objects per query. A registered agent can keep using its assignment during a Firebolt Operator restart.

The assigned Service is headless, ready-only, and named for the Engine UID and generation. Its selector never switches to another generation. The StatefulSet peer-discovery Service, which publishes not-ready addresses, is not a query destination.

Envoy resolves generation Services by fully qualified names under `<namespace>.svc.cluster.local` without expanding the Pod's DNS search domains. DNS refreshes run independently of requests; opening a connection does not force a fresh lookup. Active health checks and `ignore_health_on_host_removal` keep the discovered host set usable, but DNS and health observations do not authorize Engine shutdown.

Engine lifecycle changes update routing assignments without changing Envoy's static configuration or requiring every Gateway to restart.

## Retry behavior

The Gateway retries connection failures, refused streams, resets before request headers are sent (`reset-before-request`), and a pre-work shutdown response marked `X-Firebolt-Drained`. Other resets after request delivery and arbitrary HTTP 5xx responses are returned to the client because the Engine might already have applied a request's side effects.

Retries have a finite attempt budget and remain part of the original admission. They cannot switch an already admitted request to another generation or trigger a DNS refresh.

Request bodies up to 2 MiB can be buffered for retry. Larger requests are forwarded without retry buffering. This limit affects retry coverage, not the requirement to withdraw routing before shutting an Engine down.

## Graceful Engine shutdown

The shutdown order is routing withdrawal, followed by Engine termination:

1. The replacement generation becomes ready. The Firebolt Operator publishes its immutable route and closes the old assignment, recording every registered session that could have used it.
2. Each affected agent applies the new revision and stops granting old-generation requests. Requests already admitted retain their old destination, including pending dispatch and retries.
3. The Firebolt Operator waits until every recorded session has applied the fence and has no outstanding or uncertain old-generation requests. Positive termination evidence for that Gateway's Envoy process also closes its liability.
4. Only then may the Firebolt Operator remove the old Engine Pods and Kubernetes send SIGTERM. Graceful drain checks can additionally wait for Engine query metrics before deletion.

Pod readiness, a zero-query scrape, elapsed time, a successful routing probe, and disappearance of a Pod object are not withdrawal acknowledgments. If an agent loses the processor connection without a clean completion signal, its request state becomes uncertain and blocks retirement. An agent restart in the same Pod cannot replace its old session with an empty ledger. The Firebolt Operator replaces that Gateway Pod and uses its finalizer to retain termination evidence until the old session is safely cleared.

Deleting an Instance permanently closes its routing assignments and stops its Gateways. Engine resources remain independently managed. The coordination ConfigMap retains the confirmed shutdown record until those Engine resources are deleted, so their cleanup can still verify withdrawal after the Instance is gone or the Firebolt Operator restarts. Recreating an Instance with the same name waits for the previous Engines and their retained routing record to be removed.

Engine termination remains bounded by the Pod's grace period. The Engine's shutdown implementation must account for all accepted work, including connections waiting to reach a query handler. Requests still unfinished when that budget expires can be interrupted. Disabling metric drain checks or selecting `recreate` does not bypass the Gateway withdrawal fence.
